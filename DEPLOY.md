# Deploying CampusMarket

The live site runs from the **`main`** branch. Day-to-day work happens on **`dev`**, which
never goes live until you merge it into `main`.

| Part | Host | Deploys from |
|---|---|---|
| Frontend (React) | Vercel | `main` (`vercel.json` skips every other branch) |
| Backend (FastAPI) | Render | `main` (`render.yaml`) |
| Database + files | Supabase | already set up |

Do the steps in order. Expect about an hour the first time.

---

## Step 0: Commit the deploy files and create a `dev` branch

The repo now has `vercel.json`, `render.yaml`, `campusmarket-backend/.python-version` and this
file. Commit and push them to `main`:

```bash
git add vercel.json render.yaml DEPLOY.md README.md campusmarket-backend/.python-version
git commit -m "Added deploy config"
git push origin main
```

Then create the `dev` branch you'll work on from now on:

```bash
git checkout -b dev
git push -u origin dev
```

---

## Step 1: A separate database for development (strongly recommended)

Today your Mac, your Windows PC and (soon) the live site would all share one Supabase project.
That means test posts would show up on the real site, and running a migration while developing
would change the live database before the code that needs it is deployed.

**Your current Supabase project becomes production. Create a new one for development:**

1. Go to [supabase.com](https://supabase.com) → **New project** → name it `campusmarket-dev`.
   Save the database password.
2. Copy its connection string: **Connect** (top bar) → **Transaction pooler** (port 6543).
   Replace `[YOUR-PASSWORD]` in it.
3. Copy its secret key: **Project Settings → API Keys → Secret keys** (starts with `sb_secret_`). Click the eye icon to reveal it, then copy.
4. **Before changing anything**, copy the current `DATABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`
   from `campusmarket-backend/.env` somewhere safe, such as a password manager. These are your
   **production** values, and you'll paste them into Render in Step 2.
5. In `campusmarket-backend/.env` on the **Mac**, replace `DATABASE_URL` and
   `SUPABASE_SERVICE_ROLE_KEY` with the **dev** values. Leave `SUPABASE_URL` blank; it's worked
   out automatically.
6. Create the tables in the dev database:
   ```bash
   cd campusmarket-backend
   uv run alembic upgrade head
   ```
7. Make the same `.env` change on the **Windows** PC.

The dev database starts empty, so sign up again locally. Storage buckets are created
automatically on your first upload.

## Step 2: Backend on Render

1. Sign in at [render.com](https://render.com) with GitHub, and allow access to the
   `campusmarketplace` repo.
2. **New → Blueprint** → choose the repo. Render reads `render.yaml` and shows the
   `campusmarket-api` service.
3. It asks for the secret values. Use your **production** values from Step 1.4:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | production Supabase connection string |
   | `SUPABASE_SERVICE_ROLE_KEY` | production secret key (`sb_secret_…`) |
   | `CORS_ORIGINS` | `["http://localhost:5173"]` for now; you'll change it in Step 4 |
   | `ALLOWED_EMAIL_DOMAINS` | `["medhaviskillsuniversity.edu.in"]` |
   | `SMTP_USERNAME` | your Gmail address |
   | `SMTP_PASSWORD` | your Gmail **app password** (same as in your `.env`) |
   | `SMTP_FROM` | your Gmail address |

   `JWT_SECRET_KEY` and `OTP_PEPPER` are generated by Render automatically.
4. Click **Apply** and wait for the first deploy (about 3–5 minutes). The log should end
   with `Uvicorn running on http://0.0.0.0:…`.
5. Open `https://campusmarket-api.onrender.com/health` (your exact address is shown at the top
   of the service page). You should see `"status":"ok"` and `"storage":"supabase"`.

---

## Step 3: Frontend on Vercel

1. Sign in at [vercel.com](https://vercel.com) with GitHub → **Add New… → Project** → import
   `campusmarketplace`.
2. Leave **Root Directory** as `./`. The framework (Vite) and build settings come from
   `vercel.json`.
3. Open **Environment Variables** and add:

   | Name | Value |
   |---|---|
   | `VITE_DATA_SOURCE` | `live` |
   | `VITE_API_BASE_URL` | `https://campusmarket-api.onrender.com/api` (your Render address + `/api`) |

4. **Deploy**. You'll get an address like `https://campusmarketplace.vercel.app`.
5. In **Settings → Git**, check that **Production Branch** is `main`.

`VITE_…` values are baked in when the site is built. If you ever change one, redeploy
(Deployments → ⋯ → Redeploy).

---

## Step 4: Connect the two

The backend only accepts requests from the addresses listed in `CORS_ORIGINS`.

1. Render → `campusmarket-api` → **Environment** → edit `CORS_ORIGINS`:
   ```
   ["https://campusmarketplace.vercel.app"]
   ```
   Use your exact Vercel address: `https://`, no trailing slash, inside `["…"]`.
2. **Save Changes**. Render redeploys by itself.

## Step 5: Test the live site

Open the Vercel address and go through:

- [ ] Sign up with a college email. **The OTP email arrives.** If it doesn't, see Troubleshooting.
- [ ] Log in, then open Profile and upload an avatar.
- [ ] Post a listing with a photo, and open it on your phone.
- [ ] Post a resource with a PDF: page 1 is sharp and pages 2–4 are blurred.
- [ ] Refresh the browser on a page like `/resources/1`. It should load, not show a 404.
- [ ] From a second account, request access; the first account sees it under Notifications.

## Everyday workflow

```bash
git checkout dev            # work here, as you do now
# ...make changes, test locally (against the dev database)...
git add -A && git commit -m "…" && git push      # safe: nothing goes live
```

**To release**, when `dev` is working:

```bash
git checkout main
git pull
git merge dev
git push                    # Vercel + Render deploy automatically (a few minutes)
git checkout dev            # go back to working
```

**Database changes:** run `uv run alembic upgrade head` locally, which only affects the dev
database. When you release, Render runs the same migration on production by itself before
starting the new code. Prefer additive changes (new tables or columns), so the old version
keeps working for the minute or so while the new one starts.

**Rolling back a bad release:** Vercel → Deployments → pick the previous one → **Promote to
Production**. Render → Events → **Rollback**. Database migrations are not undone by a
rollback.

## Sending email in production

Render's free plan blocks outgoing SMTP (Gmail), so the live backend sends OTP emails through
**Brevo**, which works over HTTPS. It's free for up to 300 emails a day.

1. Sign up at [brevo.com](https://www.brevo.com).
2. **Senders, Domains & Dedicated IPs → Senders → Add a sender**: use the same address as
   `SMTP_FROM`, then click the confirmation link Brevo emails you.
3. **SMTP & API → API Keys → Generate a new API key**, then copy it (it starts with `xkeysib-`).
4. Render → `campusmarket-api` → **Environment** → **Add variable** `BREVO_API_KEY` = the key →
   **Save and deploy**.
5. `https://<your-render-address>/health` should now include `"email":"brevo"`.

Locally, leave `BREVO_API_KEY` blank and Gmail SMTP keeps working.

## Troubleshooting

| Symptom | Fix |
|---|---|
| "Failed to fetch" on every request | `CORS_ORIGINS` on Render doesn't exactly match the Vercel address, or `VITE_API_BASE_URL` is wrong. Check both, then redeploy Vercel. |
| First request after a while takes ~1 minute | Normal on Render's free plan: the backend sleeps after 15 minutes idle. The Starter plan (~$7/month) stays awake. |
| "We couldn't send the code" / OTP email never arrives; Render logs show `SMTP send … failed` | Render's free plan blocks outgoing SMTP. Set `BREVO_API_KEY` on Render (see *Sending email in production* below). `/health` then shows `"email":"brevo"`. |
| Uploads fail with "File storage is unavailable" | `SUPABASE_SERVICE_ROLE_KEY` on Render is wrong or missing. It must be the **production** project's key. |
| 404 when refreshing a page | `vercel.json` is missing from `main`. |
| A deploy failed on Render | Open the deploy's log. `uv sync --frozen` failing means `uv.lock` is out of date: run `uv lock` locally, commit, and push. |
| Logged out after deploying | Expected the first time: production signs logins with its own secret, so log in again. |
